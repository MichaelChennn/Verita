# AI 科技日报 — 立项书（v0.1 草案）

> 状态：草案，等待确认 · 日期：2026-10-19
> 前身：Verita（AI 知识社区 + 每日 Digest）

---

## 1. 为什么重新开始：对 Verita 的复盘

Verita 最初是从“AI 科技日报”这个想法出发的，后来逐渐加进了发帖、评论、投票、话题订阅和推荐 Feed，最终变成了一个**社区产品**。它现在像玩具而不是工具，根本原因有三个：

| 问题 | 说明 |
|---|---|
| **双边网络的冷启动** | 社区要同时有创作者和读者才有价值。没有用户就没有内容，没有内容也就留不住用户。一个人用的时候，社区功能的价值是 0。 |
| **价值核心被稀释** | 真正能单独给人带来价值的只有 Daily Digest，但在产品里它只是 Feed 中的一张卡片，还要先登录、先订阅话题才能看到。 |
| **工程复杂度与价值不匹配** | 4 个微服务、3 个数据库、MinIO、K8s/Helm、Terraform、Ansible、监控……这些是课程要求的工程展示，但对“每天读一份日报”这件事来说是纯负担，也让迭代变慢。 |

**结论：** 只保留“每天自动生成一份高质量 AI 日报”这一个核心价值，把它做到自己每天都愿意打开。其他东西一律不做。

## 2. 一句话定位

> **每天早上，一份为中文 AI 开发者自动生成的 AI 技术日报：5 分钟读完，每一条都能追溯到一手来源，不需要人工校对。**

### 已确定的关键决策

| 决策 | 选择 | 含义 |
|---|---|---|
| 首要目标 | 先服务好我自己 | 第一阶段只有一个用户：我。成功标准是“我每天真的在读”，不是用户数。 |
| 目标读者 | 中文 AI 开发者 | 中文写作；信源以英文一手资料为主。“英文一手资料 → 中文精炼”本身就是核心价值。 |
| 分发渠道 | 网站 + RSS | 静态站点存档每一期，RSS 推送全文。不需要账号、不需要登录。 |
| 人工参与 | **全自动** | 每天直接看到成品，不需要人工纠正。所以**质量保障必须靠系统本身**（见第 6 节），这是本项目最重要的技术挑战。 |

## 3. 用户与使用场景

**用户画像（v1 = 我自己）：** 在做 AI 相关开发 / 学习的中文开发者，英文阅读没问题但没时间每天刷 X、Reddit、HN、arXiv、GitHub。

**核心场景：**
- 早上通勤或上班前，用 RSS 阅读器或浏览器花 5 分钟看完今天的日报。
- 看到感兴趣的条目，点链接直达原始来源（论文 / Release / 官方博客）。
- 偶尔回头翻某一天的存档，查“那个模型是哪天发的”。

**用户要完成的任务（JTBD）：**
1. **不错过**真正重要的东西（重大模型发布、关键开源工具、高影响力论文）。
2. **不浪费时间**在炒作、营销号和重复报道上。
3. **快速判断**某件事和我有没有关系、值不值得点进去看。

## 4. 产品原则

1. **一手来源优先**：官方博客、论文、GitHub Release、Hugging Face 模型页。二手解读只能作为“热度信号”，不能当作事实来源。
2. **每条可追溯**：每一条都必须附上原始链接。没有来源的内容不允许出现。
3. **少而精**：每期 8–12 条。宁可漏掉，也不要掺噪音。
4. **对开发者有用**：每条不只说“是什么”，还要说“为什么对开发者重要 / 能拿来做什么”。
5. **宁缺毋滥**：生成或校验不过关的条目直接丢掉，不自动“修正”。
6. **零摩擦阅读**：不注册、不登录、无广告、无弹窗。

## 5. 范围

### v1 要做（MVP）
- 每天定时自动抓取固定信源。
- 去重、事件聚类（多个来源报道同一件事时合并成一条）、跨天去重（昨天报过的今天不重复）。
- 按“重要性 + 对开发者的实用性”打分、排序、筛选。
- 生成中文日报（结构见 7.2），并经过自动质量校验。
- 发布到静态网站（含历史存档页）+ RSS（全文）。
- 失败时降级发布（只放标题 + 链接），不能整期空白。

### 明确不做（非目标）
- ❌ 账号、登录、个人主页
- ❌ 发帖、评论、点赞、关注等任何社交功能
- ❌ 个性化推荐 / 话题订阅（v1 只做一份所有人共用的日报）
- ❌ 移动 App、后台管理界面
- ❌ 微服务、数据库、K8s
- ❌ 邮件 Newsletter（v1 之后再考虑）

> 有新想法时，先对照这张清单。想加进来就必须回答：“它能不能让我**更愿意每天读**？”

## 6. 全自动下的质量保障（核心难点）

既然没有人工审核，可信度就只能靠流水线中的多道“闸门”来保证：

| 阶段 | 机制 | 防止的问题 |
|---|---|---|
| 信源 | 白名单 + 分级（Tier 1 官方/一手，Tier 2 社区热度信号） | 营销号、谣言 |
| 抓取 | 尽量拿全文或完整摘要，而不只是标题 | 只凭标题脑补 |
| 去重 | URL 归一化 + 标题/语义相似度聚类；和过去 7 天已发布条目比对 | 重复报道、炒冷饭 |
| 排序 | LLM 按固定 rubric 打分（重要性、实用性、新颖性），再结合热度信号（HN 分数、GitHub star 增速等） | 噪音上榜 |
| 生成 | 只允许依据输入材料写作；结构化输出；每条必须引用输入中的 source ID | 幻觉 |
| 程序校验 | 引用的 source ID / URL 必须真实存在于输入集；数字和模型名要能在原文中找到 | 编造链接、编造参数 |
| LLM 自检 | 用一次独立调用检查“摘要是否忠实于原文”，不通过就**丢弃该条** | 夸大、曲解 |
| 降级 | 生成失败时发布“标题 + 链接”版；连续失败时告警（如 GitHub Actions 失败通知） | 空白日报 |

**每周 5 分钟调优（不是每日校对）：** 每周回顾一次，在一个 YAML 文件里给条目标注“有用 / 噪音 / 错误”，用来调整信源权重和打分 prompt。这是对系统的调优，而不是对每期内容的人工修正。

## 7. 产品形态

### 7.1 v1 信源清单（初稿，M1 阶段验证覆盖率）

| 类别 | 信源 | Tier |
|---|---|---|
| 官方博客 | OpenAI、Anthropic、Google DeepMind、Meta AI、Mistral、Qwen、DeepSeek、Hugging Face Blog 等（RSS） | 1 |
| 论文 | Hugging Face Daily Papers（已经过社区筛选）、arXiv cs.CL / cs.LG / cs.AI | 1 |
| 开源 | 关注仓库的 GitHub Releases（vLLM、Ollama、llama.cpp、LangChain、transformers 等）、GitHub Trending（AI 相关） | 1 |
| 模型 | Hugging Face Trending Models（过滤量化 / 合并等噪音，Verita 已有这部分逻辑） | 1 |
| 社区信号 | Hacker News（AI 相关高分帖）、Reddit r/LocalLLaMA / r/MachineLearning 热帖 | 2 |

### 7.2 每期结构

```
2026-10-20 · AI 科技日报

今日要点（3 句话说清今天最重要的事）

🔥 头条（3–5 条）       重大发布 / 重要事件，每条 3–4 句 + 来源
🧠 模型                 新模型与权重发布
📄 论文                 2–3 篇值得关注的论文，一句话贡献 + 为什么重要
🛠 开源与工具           值得关注的 Release / 新项目
⚡ 快讯                 一句话 + 链接
```

每条包含：中文标题 · 2–3 句“是什么 + 对开发者意味着什么” · 来源链接（可多个） · 标签。

## 8. 技术方案（极简优先）

```
GitHub Actions (cron, 每天 UTC 22:00 ≈ 北京时间 06:00)
   │
   ▼
Python 流水线：fetch → normalize → dedupe/cluster → score → generate → verify → render
   │                                                          │
   ▼                                                          ▼
data/YYYY-MM-DD/*.json（原始候选 + 最终日报，提交回仓库）    site/（静态 HTML + RSS）
                                                              │
                                                              ▼
                                                    GitHub Pages / Cloudflare Pages
```

- **无服务器、无数据库**：Git 仓库本身就是存储，历史数据用于跨天去重和回顾。
- **单一 Python 项目**：一条命令可以在本地完整跑一遍（`python -m daily run --date 2026-10-20`），方便调试。
- **LLM**：通过配置切换 provider。打分用便宜的模型，生成和自检用更强的模型。每日成本在 M2 实测后确定，目标是“几乎可以忽略”。
- **可复用的 Verita 资产**：
  - `genai-service/app/services/external_sources.py`：GitHub / HF / GNews 抓取逻辑、HF 噪音过滤规则
  - `genai-service/app/services/digest_generator.py`：结构化输出、source ID 引用校验的思路、重试逻辑
  - `genai-service/app/services/output_sanitizer.py`：输出清洗
  - LLM provider 抽象（含本地 Ollama 支持）

## 9. 成功指标

**产品（个人使用阶段）**
- 连续 30 天，每天都打开日报（自我记录）。
- 每期至少 1 条“如果没看到会错过”的内容。
- 每周回顾中，“噪音”占比 < 20%，“错误”（事实错误或链接错误）为 **0**。

**系统**
- 按时发布成功率 ≥ 95%（降级版也算发布，空白不算）。
- 端到端运行时间 < 15 分钟。
- 每日 LLM 成本 < 预算上限（M2 时确定具体数值）。

## 10. 里程碑

| 里程碑 | 内容 | 验收标准 |
|---|---|---|
| **M0 立项** | 本文档；确定仓库处理方式 | 文档确认 |
| **M1 信源与数据** | 实现所有 fetcher，输出每日原始候选 JSON；去重与聚类 | 连续跑 7 天，人工抽查：重要事件覆盖率 ≥ 90% |
| **M2 生成与质量闸门** | 打分、生成、程序校验、LLM 自检、降级 | 回放 M1 的 7 天数据，错误条目为 0，自己觉得“能读” |
| **M3 发布** | 静态站点 + RSS + 定时任务 + 失败告警 | 无人干预自动发布 3 天 |
| **M4 自用期** | 自己每天读，每周调优一次 | 达成第 9 节的产品指标 |
| 之后 | 视自用情况决定：邮件订阅、周报、话题筛选、分享给同学 / 同事 | — |

## 11. 风险

| 风险 | 应对 |
|---|---|
| LLM 幻觉 / 夸大 | 第 6 节的多道闸门；不通过的条目直接丢弃 |
| 信源 API 限流或变更 | 每个 fetcher 相互隔离，单个失败不影响整体；优先使用 RSS 和官方 API；失败时告警 |
| 内容版权 | 只做摘要和评述，不转载全文，始终附原文链接 |
| 范围蔓延（重蹈 Verita 覆辙） | 第 5 节的非目标清单；加任何功能前先回答“它能不能让我更愿意每天读” |
| 质量平庸、不想读 | M4 每周调优；把 prompt 和 rubric 当作产品核心来迭代 |
